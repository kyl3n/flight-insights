Q22 FLIGHT LAB - ARCHITECTURE, DIAGNOSTICS AND CODEX HANDOFF

Revision 1.0 | 3 October 2026 | Design specification, not an application release

This document incorporates the user's earlier Q22 logging, hardware and baseline-comparison requirements.


01  DECISION AND SCOPE

Build Q22 Flight Lab as an offline-first native desktop application for Windows, macOS and Linux. Use a Tauri 2 shell, React/TypeScript interface, and a packaged Python analysis engine. This is a design and research handoff for Codex, not an application release.

The product has two linked workflows: record and monitor available health signals during a flight; collect and deeply analyze the complete flight evidence after landing. The ground station remains responsible for flight control. The app explains measurements, identifies problems and proposes controlled investigations or tuning candidates. It does not replace ArduPilot failsafes or directly control the aircraft.

Make collection simple after initial setup: Start flight recording preserves short-lived sources; Collect flight logs finds local/SD-card logs, retrieves accessible completed controller logs, matches the records to a flight, and explains every unavailable source. A post-flight button cannot recreate telemetry or radio history that was never recorded.

The preferred user experience is an installed app with its runtime bundled. Users should not need Python, Node, a terminal, an API key or a cloud account. Tauri supports packaged external binaries; platform-specific building and validation are required [R01]. A hosted-only website is a poor primary fit for unrestricted log sizes, unattended local collection and native device access.

The analysis core is deterministic and versioned. Optional language-model explanations can be added later, but measured values, fault classification and parameter proposals must come from inspectable algorithms and source evidence. An AI-generated narrative is never a substitute for a validated diagnostic rule.

This specification is intentionally broader than a simple graph viewer. A complete release includes data-quality checks, aircraft health, control/filter analysis, energy comparisons, collection recovery, issue tracking, immutable tuning baselines and explainable live alerts. Features awaiting actual device samples must be labeled unvalidated or unsupported, not represented by synthetic success.

Decision: App type
Selection: Local native desktop
Reason / boundary: Large logs, USB/SD access, offline field use and background recorders.

Decision: Initial platform
Selection: Windows x64 first; Linux x64 and macOS next within the same architecture
Reason / boundary: Matches the Mission Planner ground station; cross-platform installers remain a release requirement.

Decision: Main action

Reason / boundary: A configured collection job with per-source outcomes, not an indiscriminate disk/network scan.

Decision: Tuning authority
Selection: Review and export proposals only
Reason / boundary: No automatic parameter writes, arming, mode changes or flight commands.

Decision: Data location
Selection: Local by default
Reason / boundary: No mandatory cloud upload, account or live internet dependency.

03  PRODUCT REQUIREMENTS AND COVERAGE CONTRACT

“Monitor everything important” means every relevant subsystem is represented, with its evidence status and limits visible. It does not mean declaring a subsystem healthy when the necessary sensors or logs do not exist.

Each domain has five independent concepts: evidence availability, data quality, observed condition, diagnostic confidence and issue workflow state. Do not combine them into one aircraft-health percentage. A coverage indicator can describe the fraction of required evidence present, but its label must say evidence coverage and expose its denominator.

All findings must be reproducible from a source hash, parser/rule version, aircraft-profile snapshot and selected interval. The system must retain rejected or incomplete inputs in the collection manifest and explain why a metric or recommendation was withheld.

Domain: Data integrity
Required result: Identity, source coverage, gaps, corruption, duplicates, reboot boundaries, clocks, logging performance
Examples of unavailable evidence: A TLOG cannot replace high-rate onboard data or reconstruct downlink losses.

Domain: Vibration / IMU
Required result: Per-sensor vibration, clipping, gyro spectra, sensor errors and redundancy
Examples of unavailable evidence: VIBE is not a frequency spectrum; a post-filter trace cannot show unlogged pre-filter energy.

Domain: Control / tuning
Required result: Attitude/rate/position tracking, lag/overshoot, PID terms, saturation, filter trade-offs
Examples of unavailable evidence: Gain advice is withheld without representative excitation, noise evidence and actuator context.

Domain: Power / propulsion
Required result: Pack power/energy, voltage under load, ESC electrical/thermal/RPM data, motor balance and output demand
Examples of unavailable evidence: No individual-cell diagnosis without cell data; no thrust efficiency without thrust or a validated model.

Domain: Navigation / estimator
Required result: GPS quality, estimator innovations/status, lane changes, heading consistency and position/height response
Examples of unavailable evidence: A good GNSS fix alone cannot prove trustworthy navigation.

Domain: Control path / failsafes
Required result: Pilot command, GCS receipt/transmission, onboard input and response, mode/failsafe transitions
Examples of unavailable evidence: RCIN alone does not prove the GX12 USB input reached the GCS correctly.

Domain: RF / network / video
Required result: Both radios, HTTP collection health, link/throughput indicators, GCS network and video diagnostics
Examples of unavailable evidence: RSSI alone does not identify interference or explain a video freeze.

Domain: Controller / GCS system
Required result: Scheduler/load/logging health, resets, rails, disk space, PC sleep and recorder interruptions
Examples of unavailable evidence: Low-rate telemetry may miss a transient reset cause or short electrical event.

Domain: Configuration / experiments
Required result: Firmware-aware parameter diff, hardware revision, baseline regression, matched-condition comparisons
Examples of unavailable evidence: One changed flight does not prove a change caused an improvement.


04  ARCHITECTURE AND TECHNOLOGY DECISIONS

Use a modular desktop application, not a collection of separately launched scripts. Keep native access, numerical work and presentation behind explicit contracts.

The shell supervises one engine coordinator. The coordinator owns catalog writes and schedules bounded parser/analysis worker processes. Live recorders run independently of heavy FFT/import jobs, with queues and backpressure. A large post-flight import must not starve live recording. If the UI closes during recording, offer Keep recording in tray, Stop and close, or Cancel; never silently abandon a recording.

Use newline-safe framed IPC or JSON-RPC with explicit request IDs, protocol version, cancellation, progress and errors. Route diagnostic logging to stderr so it cannot corrupt protocol messages. Return references and bounded chart slices, not entire multi-gigabyte arrays over IPC. Handle sidecar crash/restart without losing completed archives or presenting stale values as live.

A local HTTP API can exist as a development-only alternative. If added in production later, bind loopback only and enforce per-launch authentication, strict origin/host checks and narrow endpoints. It should not be necessary for the first installed app.

Lock dependency versions only after the first cross-platform packaging spike. Do not copy exploratory environment versions from this conversation into a release. Verify Python wheels, native dependencies, webview behavior, serial access and filesystem permissions on clean Windows/macOS/Linux machines.

Electron is a reasonable fallback if Tauri's platform webviews block required interaction or packaging, but it adds a bundled browser runtime. Python/Qt is viable for a team prioritizing one implementation language; it is less aligned with the proposed rich web-style chart workspace. A PWA is useful as a future report viewer, not the main collector. The recommended choice remains Tauri plus Python.

Component: Desktop shell
Decision: Tauri 2 / Rust
Responsibility: Window, native file dialogs, allowed paths/devices, OS credentials, process lifecycle and packaging.

Component: Interface
Decision: React + TypeScript + Vite
Responsibility: Stateful working surfaces, collection progress, findings, comparisons and accessible navigation.

Component: Charts
Decision: Apache ECharts; narrow series payloads
Responsibility: Linked time-series, spectra, spectrograms, scatter plots and event overlays. Benchmark rather than assuming advertised point counts [R03].

Component: Engine
Decision: Packaged Python with pymavlink, NumPy, SciPy and PyArrow
Responsibility: Decoding, units, segmentation, DSP, diagnostics, local collectors and report generation.

Component: Metadata
Decision: SQLite, single writer
Responsibility: Profiles, sessions, manifests, alignment records, findings, experiment history and job state.

Component: Numeric store
Decision: Partitioned Parquet; DuckDB queries
Responsibility: Out-of-core column selection and time-window queries. Parquet filter/projection pushdown supports this design [R02].

Component: IPC
Decision: Typed request/event envelopes over supervised stdio
Responsibility: Renderer invokes limited Rust commands; Rust routes to engine. No production HTTP server is required.

Component: Packaging
Decision: Per-OS CI builds with bundled engine
Responsibility: Windows installer, macOS app/DMG, Linux AppImage and/or supported package. Sign/notarize release builds where required.


05  INTERNAL BOUNDARIES AND REPRODUCIBILITY

Separate collection, decoding, interpretation and advice so new log formats or firmware revisions cannot silently alter old conclusions.

The engine should also provide a headless CLI with the same analysis core for repeatable batch tests and engineering review. The desktop app remains the normal user entry point. CLI and UI must not have different numerical implementations.

Before reusing FilterReview/PIDReview or other third-party code, inventory licenses and notices for every file and submodule. ArduPilot WebTools identifies GPL-3.0 licensing; decide a compliant reuse/distribution approach rather than assuming it is permissively licensed. Pin commits and document intentional changes. A rewritten implementation still needs independent numerical validation [R07].

Use a content-addressed raw store (SHA-256) and immutable per-flight manifests. Stream to a temporary file, flush, hash and atomically commit; preserve file size and source metadata. Hash equality deduplicates bytes, not necessarily flight identity. Different source devices may legitimately contain overlapping observations.

Store data tables by flight/source/boot epoch/message group, with explicit schema versions. Do not load every message from a large raw-gyro log into Python dictionaries. Parse in batches, write Parquet, query only required columns/windows and compute plot decimation separately from metric calculation.

Never execute commands or render active markup from a filename, STATUSTEXT, radio response or imported note. Validate archive extraction paths, input sizes and decoder resource limits. Plugin adapters are trusted installed code; a log is data, not a plugin.

- Collector adapter: discover, probe capabilities, start/stop recording, list completed records, retrieve, resume and report a recovery action. Its output is original bytes plus a manifest; it does not invent engineering units.

- Parser adapter: sniff file structure, decode messages, retain source identity and raw timestamps, emit schema/unit metadata, records and corruption/truncation reports. Use file content as well as extension.

- Normalizer: map validated fields into typed signals, apply scaling exactly once, preserve instance/output mapping and mark missing/sentinel values explicitly.

- Clock service: create boot epochs, estimate or accept time transforms, retain anchors/residuals/uncertainty and refuse unjustified synchronization.

- Segmenter: propose armed/airborne/hover/cruise/climb/descent/turn/transient phases with confidence; let the user correct them. Segments have versioned definitions.

- Metric service: compute descriptive results using validated units and eligible intervals. Return denominator, data coverage, uncertainty and excluded intervals.

- Rule engine: evaluate versioned prerequisites, findings and hypotheses. Rules are deterministic, testable and explicitly distinguish published thresholds from engineering heuristics.

- Recommendation planner: convert supported findings into inspection, collection, configuration review or a bounded experiment. It must abstain from a parameter value when the evidence is insufficient.

- Report service: freeze the input manifests, versions, figures, findings and limitations into portable JSON plus human-readable HTML/PDF. Regeneration does not overwrite earlier reports.


06  CORE DATA MODEL

The machine-readable contract in this handoff defines the same entities. Add schemas and migrations before implementation relies on them.

Use integer microseconds/nanoseconds for persisted clock values. Preserve UTC epoch precision: serialize 64-bit absolute times as decimal strings over JavaScript-facing JSON, or use a typed binary format; use floating relative seconds only for plotting. Null means unavailable. Zero is reserved for a real decoded zero with valid quality.

Preserve original message definitions, FMT/FMTU units/multipliers and the parser's scaling behavior. Store both the original field reference and the normalized quantity. Unknown units remain unknown. A firmware upgrade can require a new mapping, not an automatic application of the previous scale.

SQLite is the catalog and issue history; Parquet holds large numeric arrays. DuckDB is a local query engine over those tables, not a second competing metadata authority. Limit concurrent writers and make migrations recoverable.

Entity: AircraftProfileVersion
Required contents: Aircraft ID; board/firmware identity; physical motor map; ESC instance mapping evidence; motors/props/battery; calibration status; hardware changes; limits and their provenance.

Entity: FlightSession
Required contents: UUID; aircraft profile version; operator/test notes; mass/payload/battery/weather; actual parameter snapshots; source IDs; proposed and confirmed flight intervals.

Entity: SourceManifest
Required contents: Original name/location; SHA-256; byte size; device and software identity; acquisition method; start/end clocks; parser version; success/partial/error status; warnings.

Entity: SignalSchema
Required contents: Source message/field; physical quantity; raw and engineering units; scaling provenance; sensor/ESC/system/component instance; expected and observed cadence; sentinels.

Entity: Sample / event
Required contents: Source ID; boot epoch; source sequence/message offset; raw time; time domain; normalized time if valid; value or null; quality flags.

Entity: TimeAlignment
Required contents: Source and target clocks; anchor pairs; affine/piecewise transform; offset/drift; fit residuals; uncertainty; confidence; user adjustments and provenance.

Entity: MetricResult
Required contents: Algorithm/version; interval and phase; value/unit; count and time coverage; exclusions; uncertainty; source/field references; interpretation limits.

Entity: Finding
Required contents: Rule/version; severity; evidence quality; confidence; observation; competing hypotheses; evidence intervals; next action; expected result; parameter applicability; retest criteria.

Entity: ParameterSnapshot / proposal
Required contents: Immutable original; parsed values; firmware metadata; before/after diff; reason; target aircraft; validation status; rollback snapshot; no implicit application.

Entity: Experiment / issue
Required contents: Baseline and candidate; one functional change; confounders; planned success criteria; repetitions; results; open/investigating/retest/resolved history.

Entity: CollectionJob
Required contents: Per-adapter state/progress; resumable transfer position; retries; chosen flight grouping; missing-data consequences and recovery instructions.


07  COLLECTION EXPERIENCE AND RECOVERY

Configure once, then use two clear buttons: Start flight recording and Collect flight logs. Collection is a coordinated job whose partial results remain useful.

- First use: select aircraft/profile; choose approved Mission Planner/QGC and camera folders; identify controller USB device; enter radio addresses; confirm optional forwarded telemetry. Each optional source may be skipped.

- Start flight recording: verify disk space, clock status and recorder reachability; open a session envelope; begin configured ground/RF/system recorders. Show live sample ages and whether each source is actually producing records.

- Collect flight logs: scan configured folders and mounted SD log directories; query a configured available controller after disarming; include RF/system captures; copy selected records to the raw archive; hash and validate each transfer.

- Match records using aircraft/system IDs, boot identity, time anchors and file intervals. File modification time alone is weak evidence. Propose ambiguous groupings and ask the user to choose; do not merge unrelated flights merely because they were imported together.

- Run completeness checks before deep analysis. Show each source as collected, partial, still recording, unavailable, unsupported, failed or not configured. State which analyses are blocked and provide a source-specific next action.

- Resume an interrupted transfer only after confirming device/log identity and consistency. Never mark a growing or incomplete remote log complete. Retain successfully collected sources if another adapter fails.

- Watch configured directories only after the user enables auto-collection. Detect stable file size/closed recordings before ingestion; treat open TLOGs as provisional. Avoid full-disk scanning, uncontrolled network sweeps or opening every serial port.

Failure: Controller port busy
User-facing recovery: Disconnect the GCS from that USB port, retry, or use its downloader/SD card. Preserve the controlling GCS during flight.

Failure: Aircraft armed / active log growing
User-facing recovery: Defer the onboard transfer until a completed log is available. Keep live recording active.

Failure: No TLOG found
User-facing recovery: Choose the actual GCS log directory; verify recording before the next flight. Do not claim recovery of packets never logged.

Failure: RF history absent
User-facing recovery: Explain that live capture was required; test the configured endpoints and start recording next time.

Failure: Unknown vendor format
User-facing recovery: Archive it, identify device/firmware and request one representative export/schema. Give manual export instructions when documented.

Failure: SD card or disk full / sleep interruption
User-facing recovery: Show the exact interrupted interval, preserve completed data and explain the recording gap.

Failure: No optional camera/system log
User-facing recovery: Keep flight analysis available; mark camera/system conclusions unassessed.


08  SOURCE ADAPTERS AND HARDWARE CAPABILITIES

Implement adapters as capability-driven integrations. “The model supports a feature” and “this installed firmware produced that measurement” are different facts.

For SkyPulse, the documented read-only GET endpoints are /scatter_data.json and /events.json, with about 50 seconds of history. Preserve every poll and failure. Dataset windows overlap; derive deduplicated samples only after validating the exact sample identity/time schema. Collection time bounds when the reply was observed, not when every point inside it occurred. A five-second poll interval is a proposed starting point to bench-test, not a guaranteed vendor requirement [R10].

Do not compete with Mission Planner/QGC for a serial connection or silently alter MAVLink stream rates. Prefer the existing GCS TLOG for post-flight review; use explicitly configured forwarding/router duplication for the app's live monitor. Record router configuration and traffic counters. Log download should be deferred while airborne and should not saturate the control radio link.

No automatic flight command, parameter write, log deletion or firmware update belongs in the collector API. Read-only parameter/version requests and log transfers must be explicit capabilities with tests that inspect all outbound MAVLink messages.

Adapter: ArduPilot DataFlash
Required behavior: BIN and textual DataFlash LOG; FMT/FMTU-aware schema; parameters, events and raw/batch sensor records
Evidence boundary: Decode supported firmware schemas; retain unknown message types and report undecoded fields.

Adapter: GCS MAVLink
Required behavior: Mission Planner/QGC TLOG and documented forwarded stream; preserve system/component IDs and receive timestamps
Evidence boundary: Separate GCS-sent, vehicle-sent and routed/duplicate messages where the capture allows it.

Adapter: Controller download
Required behavior: Read-only LOG_REQUEST_LIST/DATA/END baseline; optional tested MAVFTP acceleration; SD import fallback
Evidence boundary: Capability-probe firmware and paths. Do not require newer virtual paths on a 4.7.1-era controller [R11, R12].

Adapter: SkyPulse air/ground
Required behavior: Configured read-only statistics/events polling with raw responses, UTC and monotonic collection times
Evidence boundary: Manual endpoints expose rolling history. Firmware response structure and units must be verified from actual samples [R10].

Adapter: APD/ESC
Required behavior: Consume available onboard/telemetry RPM, electrical, thermal and error fields; record unsupported channels
Evidence boundary: Plain BDShot RPM is not evidence of electrical/thermal coverage. Extended telemetry capability depends on ESC/firmware [R09].

Adapter: Parameter exports
Required behavior: Mission Planner name/value and QGC formats; whole snapshots plus logged changes
Evidence boundary: Snapshot/readback identity matters; logged startup parameters may not establish an entire later flight if settings changed.

Adapter: EdgeTX / GX12
Required behavior: Optional enabled SD Logs CSV import from the radio's mounted storage after flight
Evidence boundary: USB joystick operation does not guarantee aircraft telemetry is available on the radio. Do not change USB mode during flight [R31].

Adapter: SIYI A8
Required behavior: Local media/sidecar import and documented Ethernet download where supported; camera metadata and events
Evidence boundary: Media retrieval does not imply durable diagnostic logs or measurable end-to-end latency [R19].

Adapter: Ground computer
Required behavior: Optional local timestamped recorder for disk, CPU, memory, network and process/recorder health
Evidence boundary: OS-specific capability and permissions must be tested; no hidden claims of GPU decoder or joystick visibility.

Adapter: Generic exports
Required behavior: CSV/JSONL mapping wizard with explicit units, clocks and instances
Evidence boundary: Never guess whether RSSI is dBm, a percentage or a vendor scale. Save the mapping with firmware/version.


09  TIME ALIGNMENT AND FLIGHT SEGMENTATION

A single pane of glass needs a shared timeline when evidence supports one, and visibly independent clocks when it does not.

Preserve these domains independently: FC boot/sample time; GPS week/time-of-week or validated UTC; TLOG ground receive time; PC wall clock and monotonic clock; radio-internal time; camera media time. Split at FC reboot, clock discontinuity, capture restart and counter wrap. Never sort two boot epochs into one apparent continuous flight.

Preferred alignment anchors are valid logged GNSS time paired with FC time, and MAVLink SYSTEM_TIME with valid Unix/boot values. Validate leap-second handling, time validity and source system/component. Estimate a piecewise affine transform from multiple anchors when drift matters. Store the chosen anchors, method, residual distribution and uncertainty [R13].

TLOG receive time includes link and scheduling delay. Shared arming/mode events are fallback anchors with bounded uncertainty, not proof of millisecond synchronization. Cross-correlation is a proposed alignment aid and must be labeled estimated; correlation is not causal attribution. Radio timestamps with undocumented epochs remain unaligned until verified.

Show alignment uncertainty as a range when users compare events across sources. Suppress claims that require ordering finer than the uncertainty. A statement such as “the RF drop preceded the rate error by 40 ms” is invalid if alignment uncertainty is 500 ms.

Detect armed intervals separately from airborne intervals. ARM or heartbeat state alone is not takeoff. Propose takeoff/landing from multiple available signals such as altitude change, vertical velocity, output demand and landed state. Uncertain phases must remain editable and visible.

Classify hover/cruise/climb/descent/turn/transient phases using recorded motion, commands and mode, with configurable thresholds and minimum dwell time. Initial engineering defaults can be proposed and tested, but are not universal ArduPilot limits. Store the segmentation algorithm/version and user corrections.

All metrics must state their interval and exclusions. Do not count disarmed bench time as flight energy, bridge gaps in integrated power, mix pre/post-parameter-change segments, or compare aggressive maneuvering against steady hover as an efficiency result.


10  DIAGNOSTIC POLICY AND RECOMMENDATION LEVELS

Every insight begins with an observation and can advance only as far as the evidence allows.

Severity and confidence are separate. A potentially serious but poorly evidenced condition can warrant investigation without claiming its cause. Use an evidence gap state for missing data, not a red aircraft-fault alarm. Published limits, hardware limits, user acceptance criteria and engineering heuristics must be labeled distinctly.

Each rule specifies eligible phases, minimum coverage/sample rate, debounce/dwell, hysteresis, prerequisites, exclusions, reference and firmware applicability. If a prerequisite fails, produce a specific “cannot assess” result and collection/test guidance. Avoid arbitrary global health scores.

Recommendation cards show the observation, source/fields/instances, time interval, confidence, possible causes, proposed action, expected benefit, possible trade-offs and a retest criterion. A parameter name listed as relevant is not itself a recommendation to change its value.

Do not infer physical RF packet loss from MAVLink sequence gaps alone, exact motor damage from asymmetric current alone, PID direction from high current alone, or a notch center from a VIBE summary. A diagnostic model must be validated against representative labeled fixtures before its conclusions are promoted beyond exploratory status.

Level: Observation
What the app may say: “IMU 1 clipping increased during this interval.”
Required support: Valid decoded samples, counter handling, exact source/time references.

Level: Hypothesis
What the app may say: “Mechanical vibration is a plausible contributor.”
Required support: Multiple relevant observations and competing explanations; confidence stated.

Level: Investigation
What the app may say: “Inspect the mounting, then capture pre/post gyro data.”
Required support: Action addresses an evidence gap or plausible cause; expected result defined.

Level: Configuration review
What the app may say: “Check the selected notch tracking source against actual RPM coverage.”
Required support: Exact firmware metadata and actual source capability; no assumed bitmask.

Level: Parameter candidate
What the app may say: “Evaluate this proposed change set in this bounded test.”
Required support: Validated model/method, data sufficiency, constraints, before/after values, applicability and rollback.

Level: Confirmed improvement
What the app may say: “Repeated comparable tests improved these measured outcomes.”
Required support: Predetermined metrics, matched conditions, repetitions and uncertainty; no unexplained regressions.


11  VIBRATION, CLIPPING AND IMU ANALYSIS

Prioritize mechanical and sensor health before gain optimization. Keep each IMU instance visible.

Decode the actual VIBE schema. Modern per-IMU records and older Clip0/Clip1/Clip2 layouts require different mappings. Compute axis distributions, p50/p95/p99, maxima and time spent above the published 30 and 60 m/s² guidance bands. Use time weighting for exposure and sample quantiles for distribution; label each accurately. Brief landing impacts must remain distinguishable from persistent airborne vibration [R04, R14].

Clipping values are counters: compute positive increments within each continuous boot/sensor epoch. A counter decrease is a reset/wrap/format event to resolve, not a negative clipping event. Do not attribute the initial counter value to a selected interval. Report count, rate, onset, duration and flight phase; show individual sensors before an optional aggregate.

Correlate vibration with motor RPM/output demand, speed, commanded angular motion and aircraft configuration only after alignment is established. Inspect repeated RPM orders, speed-related growth, loose mounting/cable contact, propeller balance/tracking and motor bearing candidates. These associations narrow inspection; they do not prove the mechanical cause.

Compare redundant IMUs using calibrated quantities, instances and health/error records. Check sensor disagreement, clipping, sampling discontinuities, temperature association, active primary/lane changes and unexplained estimator divergence. Do not average away a defective sensor or merge data from different sensor orientations.

If persistent clipping or major mechanical vibration exists, defer optimization proposals that could hide the symptom. The next step should prioritize inspection, sensor installation verification and a comparable confirming log. A notch filter is not a remedy for accelerometer saturation.

Acceptance: fixtures must cover high-amplitude brief impact, sustained airborne vibration, older/newer VIBE schemas, a reset inside the file, missing one IMU, unknown scale, clipped signal with absent VIBE, and a selected window beginning after an existing counter increment.


12  GYRO SPECTRA AND HARMONIC-NOTCH ANALYSIS

Implement proper raw-gyro analysis, including raw and batch formats. Frequency analysis of the low-rate VIBE envelope is prohibited.

Support eligible GYR records and ISBH/ISBD batch data through firmware-aware decoders. Reconstruct batch sequence, instance, sensor type, scaling, sampling rate and sample time; detect missing/duplicated batches. Preserve pre/post-filter identity. Verify this against a pinned ArduPilot FilterReview implementation and known fixtures; do not merely infer format from a field name [R05, R07].

Within stationary-enough segments, remove the mean or documented trend, apply a specified window and compute Welch PSD with recorded sample rate, FFT length, overlap, resolution and units. Report amplitude spectra and power spectra distinctly; use 20 log10 for amplitude ratios and 10 log10 for power ratios. Validate Parseval/known-sine fixtures. Do not resample across large gaps or claim resolution beyond the data duration.

Expose per-axis/per-IMU PSD, time-frequency spectrograms and RPM-order overlays. Convert verified mechanical RPM to rotation frequency using RPM/60. Electrical RPM or a pole-pair-scaled field requires the correct telemetry conversion first. Never apply motor-pole scaling twice. Blade-pass orders require the actual blade count, not an assumption.

Compare pre/post-filter noise only for matching sensor, phase, sample provenance and scale. Calculate band power reduction and residual peaks. A lower plotted post-filter peak is not automatically better if filtering adds harmful control-band delay or the flight conditions differ.

Candidate notch planning checks source coverage and freshness, whether dominant peaks track RPM/throttle/FFT, relevant harmonics, width, attenuation, minimum-frequency behavior, phase delay and controller load. Prefer the smallest supported filter set that addresses repeatable noise. Model with the exact firmware filter equations and parameters, including a second notch bank and dynamic options where available [R06].

Relevant parameter families include INS_HNTCH_*, INS_HNTC2_*, INS_GYRO_FILTER, gyro/raw logging configuration and applicable ESC/RPM source settings. Resolve each name, range, bitmask and reboot requirement from the installed firmware. Do not copy wiki numeric masks when prose, versions or source definitions disagree.

A numeric candidate requires verified spectral/RPM data and firmware-correct simulation. Show predicted attenuation and delay as modeled results, then require a confirmation flight with measured residual spectra, control response, CPU/logging health and temperatures. If raw data or RPM is insufficient, recommend the exact missing capture rather than invent a center frequency.


13  ATTITUDE, PID AND ACTUATOR DIAGNOSIS

Evaluate the control chain: pilot/navigation demand, desired attitude/rate, achieved motion, PID contributions and available actuator authority.

Use ATT, RATE and PIDR/PIDP/PIDY where supported, plus actual output/motor-limit evidence. Compute phase-specific error RMSE, absolute-error quantiles, bias, lag, rise/settling time, overshoot, residual oscillation bands and repeatability. Rate-only records support fewer conclusions than full PID/output/noise evidence [R08, R14].

Step-response metrics require a suitable isolated command change, adequate amplitude, initial/final steady behavior, known sampling and enough post-command time. Use reference normalization and defined rise/settling bands. Reject overlapping commands, saturated maneuvers, clipping, major estimator resets and data gaps. Fit or average responses only across comparable maneuvers.

Estimate lag with a documented method and uncertainty; cross-correlation of highly periodic or unexcited data can be ambiguous. Frequency-response/coherence analysis requires sufficient excitation and correct interpretation of closed-loop input/output signals. Do not report gain/phase margins from an invalid transfer estimate.

Separate undertracking due to command shaping, actuator saturation, insufficient thrust, filter delay, wind/disturbance, estimator issues and gain selection. Inspect I accumulation/recovery, P/D activity, feedforward, Dmod/SRate and applicable flags. A high D-term RMS can reflect sensor noise, commanded motion or gain behavior; it is not a standalone instruction to reduce D.

Map RCOU/output channels through SERVOx_FUNCTION and the verified motor order; protocol and configured endpoints matter. PWM-like numerical bounds are not universal across DShot/scaled outputs. Use firmware motor-limit/allocator flags when available, and label output-near-bound heuristics as such. Distinguish total thrust, attitude/yaw authority and individual output limitations.

Parameter families to review include the applicable ATC_RAT_RLL_*, ATC_RAT_PIT_* and ATC_RAT_YAW_* gains/filters/limits, ATC_ANG_*, ATC_ACC_R_MAX, ATC_ACC_P_MAX, ATC_ACC_Y_MAX, ATC_INPUT_TC and relevant motor parameters. Presence and naming are firmware-dependent. Do not issue a generic recipe to increase P, reduce D or remove filtering.

A tuning plan first resolves sensor/mechanical/estimator issues, then validates filtering, then uses an appropriate controlled tuning method or ArduPilot AutoTune workflow with actual vehicle constraints. Any app-generated numerical gain candidate must be supported by a validated system-identification/optimization method; otherwise offer a test plan and evidence links. Preserve the previous accepted parameter snapshot and change one functional group at a time.


14  POWER, BATTERY AND ENDURANCE OPTIMIZATION

Energy analysis must distinguish measured consumption, comparable performance and a causal explanation for improvement.

Calculate simultaneous electrical power P(t)=V(t)×I(t). Integrate signed power over valid continuous intervals: E_Wh = sum[0.5(P_i+P_i+1)×dt]/3600. Select a declared primary battery monitor; do not sum an aggregate monitor with the same pack's constituent monitors or combine BIN/TLOG duplicates. Cross-check logged cumulative consumption only after validating its units/resets.

Retain negative current as a measured value and flag calibration/sign/returned-energy interpretation. Never silently clamp it or fill missing values with zero. Define gap tolerance from actual cadence and expected rate; exclude long or invalid intervals and show usable coverage. Distinguish total selected-interval energy from energy in only the observed portion.

Report calibrated pack voltage/current, time-weighted mean and peak power, Wh/min, phase-specific power, voltage under comparable demand, thermal trends and observed usable capacity when a valid discharge test exists. Mean cell voltage from pack voltage divided by cell count is not individual cell voltage or balance.

Hover efficiency comparisons require near-steady height/motion and comparable mass, payload, battery state/temperature, props and wind. Cruise comparisons require defined valid distance/speed and matched segments; report Wh/km only with appropriate overlapping power/navigation coverage. GPS ground speed is not airspeed, especially in wind.

A speed-versus-power curve can identify an observed operating region for lower Wh/km or lower power within the tested envelope. It cannot establish a globally optimum cruise speed from a few unmatched points. Weight-normalized power is a comparison proxy with assumptions, not a direct propulsive-efficiency measurement.

Apparent voltage drop divided by current change can screen pack-plus-wiring resistance only over suitable short segments with near-constant state of charge and temperature; report fit quality and confounders. Do not label it intrinsic cell resistance. Compare pack and per-ESC voltage/current carefully for sensor calibration and timestamp differences.

Endurance estimates are scenarios based on measured/declared usable remaining energy, selected reserve and representative future power. Show assumptions and uncertainty; 40 Ah nominal capacity alone does not establish remaining energy or a safe return time. Do not infer battery chemistry limits from “12S”.

Connect tuning to energy only when oscillation/output activity and power co-occur under comparable conditions, and then frame a hypothesis. Validate by repeated matched flights with tracking/stability/thermal constraints. Lower PID gains can worsen control; lower filter noise can add delay. The objective is a trade-off among stable response, noise, thermal load, authority and energy, not minimum watts at any cost.


15  ESCS, MOTORS, AIRFRAME AND POWER DISTRIBUTION

Use the exact physical-output-instance mapping and compare behavior within equivalent operating conditions.

For each configured motor, track available RPM, command, voltage, current, consumed charge, ESC/motor temperature and error/telemetry counters. Report channel completeness and freshness separately. All four RPM values do not establish four temperature/current streams. Check supported extended telemetry and the APD firmware before choosing a collection method [R09].

Analyze motor asymmetry only in stable, comparable phases with known mapping. Control allocation, yaw demands, wind, CG, payload and motor direction can produce legitimate differences. Persistent unexplained asymmetry should generate inspection hypotheses and a bench/mapping/calibration check, not an automatic diagnosis of a failed motor.

Look for abrupt command-to-RPM mismatch, temperature rise inconsistent with demand, telemetry loss, rail/current excursions and repeated output limiting. Require multiple signals and adequate telemetry rate before assigning mechanical/electrical causes. Identify the observed anomaly even when the cause remains unresolved.

Trend airframe/prop changes with vibration orders, phase-specific energy, tracking and durability notes. Logs alone cannot measure frame stiffness, drag coefficient or structural integrity. Add external measurement/test results as evidence rather than inferring them from a single spectrum or endurance number.

Controller, accessory and main battery rails are different. Record the actual regulator/power-module topology for the Cube and H7 profiles. POWR samples can screen logged rail behavior but cannot qualify capacitor ripple, startup transients, connector heating or the reported local capacitor ratings.

Manufacturer operating limits and user acceptance criteria are profile data with a source/version and units. No universal ESC temperature, motor-current or pack-voltage threshold should be hardcoded as safe for every installation.


16  NAVIGATION, HEADING, ALTITUDE AND CONTROLLER HEALTH

Troubleshooting should connect observed trajectory/control errors to estimator and sensor evidence without assuming a single cause.

GPS/GPA review covers fix type, satellites, HDOP and available horizontal/vertical/speed accuracy, update gaps, velocity/position discontinuities and receiver changes. Evaluate airborne intervals and required flight modes. A low satellite count or high dilution is a context signal; a reported fix is not a guarantee against interference or spoofing.

EKF review covers lane-specific innovation test metrics, status flags, timeouts, resets, lane/primary changes and aiding changes, linked to GPS, magnetometer, barometer/range and vibration data. Verify version-specific XKF/NKF scales; these test metrics are not raw covariance. For applicable XKF4 quantities, 1 marks the innovation acceptance gate, not the Copter EKF failsafe threshold. Failsafe diagnosis requires the configured FS_EKF_THRESH and matching filtering, multiple-quantity/state/timer logic; prefer explicit recorded activation [R33].

Heading review compares available magnetometers, estimated heading, yaw innovations and current-dependent changes after accounting for orientation and calibration. Association between current and field/heading may indicate interference but does not establish a cause. Do not transplant compass offsets/device IDs from another aircraft because mounting matches.

Altitude/position response uses desired versus estimated/measured motion with correctly decoded frames and sign conventions. Distinguish NED down from upward altitude. Inspect climb/descent command response, vertical oscillation, barometer/range inconsistencies, position-hold error and navigation-controller output limiting.

Controller health includes firmware/board identity, reset/watchdog/crash indications when logged, scheduler timing/load, loop delays, logging drops/buffer pressure, IMU errors, temperature and supply rails. Correlate load increases with high-rate logging, filtering and telemetry. A missing interval may be logger overload rather than a flight dynamics event.

Decode events/error-resolution semantics from the matching firmware. A historic ERR entry is not automatically an active fault; an error-clear code may close an incident. Preserve the event sequence and explicitly distinguish “no resolution captured” from “fault remains present now”.


17  RADIO, GCS, JOYSTICK AND VIDEO TROUBLESHOOTING

Represent the complete observation path: operator input -> GCS/routing -> radio -> onboard receipt -> aircraft response; video uses a separate return path.

Preserve both radios' available RSSI/quality/rate/drop/temperature/Tx-power data and raw API responses. Units, averaging windows, counter behavior and firmware are adapter metadata. Compare directional traffic and RF metrics to application demand without summing overlapping history windows. A local radio API failure may be an HTTP/network failure rather than an RF outage.

For MAVLink, separate each system/component/channel, sequence stream, send/receive direction when known, routing duplicates and signing/version metadata. Report received-stream gaps and message cadence. Sequence discontinuities alone do not measure physical RF packet loss; logger behavior, routing and multiple senders can produce them.

Track pilot input freshness and mode/command requests where available, acknowledgements and actual onboard state. If a command appears on the ground but no onboard response is captured, inspect the missing chain and alignment uncertainty. Neither absence in a partial log nor a COMMAND_ACK by itself proves physical aircraft behavior.

For the GX12 USB path, preserve the EdgeTX model/version and GCS joystick mapping as configuration artifacts. Optional OS/HID diagnostics can observe device disconnects/input timing only if the integration actually exposes them. RCIN records show what ArduPilot received; they are not raw USB joystick measurements.

Video troubleshooting separates source camera health, RTP/transport/network behavior, decoder/render load and display delay. Record codec/resolution/received bitrate/frame/decode-drop data when provided by the actual GCS/player. Avoid launching a second decoder/capture that materially loads the flight computer without an explicit configuration choice.

A recorded video or ping measurement alone cannot establish glass-to-glass latency. Provide a controlled bench latency test workflow with a synchronized visual/time reference. Correlate freezes with radio/GCS evidence only at supported clock accuracy. SIYI media download can be supported separately from diagnostic log availability [R19].

Ground-system health should record process/app version, network adapter/link changes, disk availability, sleep/resume, recorder failures and available CPU/memory/decoder indicators. Alerts must identify when the observer itself is unhealthy so the user does not mistake a stalled dashboard for stable aircraft values.


18  LIVE MONITORING AND ALERT LIFECYCLE

Live monitoring is an additional observer. Its availability and resolution depend on forwarded/recorded telemetry, and it cannot see all high-rate onboard evidence.

- Show aircraft-connected state separately from stream freshness and recorder-active state. Use receipt age and source timestamp/sequence progression; receiving the same old value repeatedly is not necessarily fresh data.

- Define expected cadence per signal/source. Use configurable dwell, hysteresis and clear conditions for alerts. Suggested engineering defaults must be labeled and validated against representative flights, not presented as official thresholds.

- Use eligible-phase rules to avoid a normal disarmed or startup state generating repeated flight alarms. Data gaps, out-of-range values and device faults are distinct incidents.

- Display serious supported observations prominently, with the source age and next diagnostic action. Optional sounds/notifications are user-controlled. Do not replace or modify ArduPilot/GCS alarms and failsafes.

- Deduplicate related symptoms into an incident while preserving individual evidence. Record first/last occurrence, count, active/cleared state, acknowledgement and subsequent recurrence.

- Acknowledge means the user saw it; it does not mean resolved. Only a documented test/retest can close an engineering issue. Preserve investigator notes and the evidence for closure.

- After flight, recompute eligible rules against the more complete onboard data. Label revisions to a live hypothesis and explain why the post-flight conclusion changed.

- On low disk, engine crash, recorder backlog or clock jump, prioritize recording continuity and explicitly mark affected intervals. The last displayed measurement must show stale age, not remain green indefinitely.

26  TROUBLESHOOTING WORKSPACES

Offer symptom-based entry points that open a useful set of signals and a short evidence-driven decision path.

Symptom: Vibration / shaking
Inspect together: VIBE/clipping, gyro orders, rates/PID, outputs/RPM, phase and speed
Next discriminating step: Separate mechanical noise from control oscillation; inspect hardware or collect missing raw evidence.

Symptom: Short flight time / high current
Inspect together: Calibrated power, mass/payload, battery state, speed/climb, RPM/output activity and temperatures
Next discriminating step: Compare matched phases; test sensor calibration and change one supported factor.

Symptom: Poor hover / altitude oscillation
Inspect together: Desired/actual vertical motion, clipping, baro/range, EKF, thrust limits and power
Next discriminating step: Identify estimate error versus actuator/control limitation before changing altitude gains.

Symptom: Yaw oscillation / drift
Inspect together: Yaw demand/response, heading innovations, CW/CCW output groups, compass/current and limits
Next discriminating step: Check commanded yaw, allocation/CG, source selection and interference context.

Symptom: Unexpected mode or failsafe
Inspect together: Mode reasons, active error events, configured timeouts, GCS/RC freshness and aircraft response
Next discriminating step: Reconstruct the event against the matching firmware; distinguish observed trigger from suspected cause.

Symptom: Missing / hot / uneven ESC
Inspect together: Mapped instances, RPM, telemetry age, current/voltage/temperature and demand
Next discriminating step: Verify mapping/capability/wiring and compare under equivalent demand; do not diagnose a stopped motor from missing telemetry.

Symptom: Video freeze / delay
Inspect together: Camera/player frames, network/decoder load, both radios, traffic demand and TLOG continuity
Next discriminating step: Separate video-only failure from common link or ground-computer failure; run a controlled latency test if required.

Symptom: App shows gaps / strange values
Inspect together: Source identity, units/sentinels, clocks/reboots, parser warnings, DSF/PM and recorder state
Next discriminating step: Correct the observation pipeline before drawing aircraft conclusions.
